# Sango Roadmap

This roadmap is organized for external contributors. Each item should be small
enough for one pull request and complete enough to be independently reviewed.

## Priority Rules

- Do items in `Required First` before taking work from later sections.
- Items in `Parallel After Required First` can be worked on at the same time.
- Each PR should include backend tests, frontend tests, or both, depending on the
  touched surface.
- Public API changes must update Utoipa annotations and OpenAPI schemas.
- Secret-related work must include negative tests proving secrets are not exposed.

## Required First

These tasks unblock most other work.

### 1. Add Real Database Migrations

Status: open

Implement a migration workflow instead of relying only on `db.push_schema()`.

Done when:

- There is a repeatable migration command for local and production use.
- Fresh databases can be initialized without `SANGO_DB_PUSH_SCHEMA=true`.
- Existing development databases can be upgraded without data loss.
- README documents migration commands.
- CI can run migrations before tests.

### 2. Normalize ID Types Across Public APIs

Status: open

Most product resources now use UUIDs. Audit every route, OpenAPI annotation, and
frontend call to ensure IDs are UUIDs where appropriate.

Done when:

- No product resource uses prefixed string IDs.
- OpenAPI path params use `Uuid`.
- Tests cover invalid UUID path params.
- Docs show UUID examples.

### 3. Add API Error Contract Tests

Status: open

Lock down the error envelope and validation behavior.

Done when:

- Route tests cover `401`, `403`, `404`, validation `400`, and internal error
  redaction.
- `axum-valid` rejections use the same error envelope as application errors.
- OpenAPI documents common error responses.

### 4. Add Contributor CI

Status: open

Create a CI workflow for pull requests.

Done when:

- CI runs `cargo fmt --check`.
- CI runs `cargo test`.
- CI runs frontend install/build.
- CI runs an OpenAPI generation smoke test.
- CI starts PostgreSQL for integration tests.

## Parallel After Required First

These can proceed independently once the required-first items are underway or
done.

## Backend And API

### 5. Implement API Token Management

Status: open

Add user-scoped API tokens for CLI/MCP automation. These are not JWTs.

Done when:

- Users can create, list, and revoke API tokens.
- API tokens are shown only once.
- API tokens are hashed at rest.
- Token auth works alongside JWT auth.
- Tests prove revoked and malformed tokens fail.

### 6. Add Refresh Tokens And Session Revocation

Status: open

JWT access tokens should be short-lived. Add refresh token rotation.

Done when:

- Login returns access token plus refresh token.
- Refresh token is opaque, hashed, and stored in DB.
- Refresh rotates the token and revokes the previous token.
- Logout revokes the active refresh token.
- Tests cover expired, reused, and revoked refresh tokens.

### 7. Add JWT Key Rotation

Status: open

Support multiple verification keys and a current signing key.

Done when:

- JWTs include `kid`.
- Config supports active signing key and old verification keys.
- Old valid tokens continue to verify during rotation.
- Tokens signed with unknown `kid` fail.

### 8. Implement RBAC And Workspaces

Status: open

Introduce organizations/workspaces, memberships, and scoped permissions.

Done when:

- Users belong to workspaces through memberships.
- Roles are scoped to workspace membership.
- Project/server/service access is workspace-scoped.
- Admin-only APIs remain platform-admin-only.
- Tests cover cross-workspace denial.

### 9. Add User Management APIs

Status: open

Expand admin user management beyond invites.

Done when:

- Admins can list, disable, reactivate, and change roles for users.
- Disabled users cannot login or use existing tokens.
- Users cannot remove the last platform admin.
- OpenAPI and tests are updated.

### 10. Add Server Connectivity Checks

Status: open

Implement safe SSH checks for Docker hosts.

Done when:

- `POST /api/v1/servers/{id}/check` validates SSH connection.
- The check runs only allowlisted commands.
- Docker availability and version are recorded.
- Private key material is never logged or returned.
- Tests cover command construction and redaction.

### 11. Add Controlled Docker Executor

Status: open

Replace placeholder deployment output with real SSH execution.

Done when:

- Image, Compose, and Dockerfile deploy commands execute over SSH.
- Commands are generated by typed builders.
- No arbitrary command endpoint exists.
- Failure output is captured as deployment output.
- Tests prove shell injection is not possible through names or paths.

### 12. Implement Temporal Workflow Starters

Status: open

Move deploy/restart/proxy/log/template work into Temporal workflows.

Done when:

- Deploy API starts a Temporal workflow.
- Restart API starts a Temporal workflow.
- Workflow IDs are persisted in deployments.
- Worker queues `high`, `default`, and `heavy` are used consistently.
- Tests use mocked activities.

### 13. Add Deployment Status Updates

Status: open

Deployment records should reflect workflow progress.

Done when:

- Status transitions from `queued` to `running`, `succeeded`, or `failed`.
- Output is appended or chunked safely.
- API can list deployment history by service.
- Tests cover success and failure transitions.

### 14. Add Service Log Collection

Status: open

Implement user-requested service logs without exporting hosted app telemetry.

Done when:

- Users can fetch recent logs for authorized services.
- Logs are collected on demand or through a controlled job.
- Platform telemetry exporters do not include app log contents.
- Tests cover RBAC and telemetry redaction.

### 15. Add Nginx Proxy Apply

Status: open

Nginx is the default proxy and should be implemented first.

Done when:

- Proxy config preview is deterministic.
- Apply writes config to the configured server path through SSH.
- Config is validated before reload.
- Reload uses an allowlisted command.
- Tests cover generated config and rollback behavior.

### 16. Add Traefik Proxy Apply

Status: open

Traefik support follows Nginx.

Done when:

- Traefik dynamic config preview is deterministic.
- Apply writes the dynamic config safely.
- TLS settings are represented correctly.
- Tests cover generated config.

### 17. Add Docker Credential Binding To Deploys

Status: open

Deployments need project-scoped Docker registry credentials.

Done when:

- Services can select project credentials.
- Deploy workflows perform `docker login` without exposing passwords.
- Passwords are decrypted only inside the activity that needs them.
- Tests prove credentials are redacted in logs and telemetry.

### 18. Add Env Var Materialization

Status: open

Service deployments need encrypted env vars materialized safely.

Done when:

- Project, environment, and service scoped env vars are resolved with precedence.
- Env files are written to controlled paths.
- Env values are redacted in API responses and telemetry.
- Tests cover precedence and redaction.

## CLI And MCP

### 19. Create Rust CLI Workspace Crate

Status: open

Implement the agent-friendly CLI described in
`docs/sango-cli-mcp-spec.md`.

Done when:

- `sango --tree` prints all commands and subcommands.
- All interactive inputs are also available as args or flags.
- `sango api` can call safe API endpoints directly.
- Errors include actionable next steps.
- CLI auth supports JWT and API token modes.

### 20. Create Rust MCP Server Workspace Crate

Status: open

Expose safe Sango operations to local agents.

Done when:

- MCP server authenticates with API tokens.
- Tools cover deploy, restart, logs, project/service lookup, and proxy preview.
- Tools never expose decrypted secrets.
- Tests cover schema and authorization behavior.

### 21. Add OpenAPI-Based Client Generation

Status: open

Share typed API models between CLI/MCP/frontend where practical.

Done when:

- OpenAPI JSON can be generated in CI.
- CLI or frontend API client uses generated types or checked schemas.
- Breaking API changes are visible in PR diffs.

## Frontend

### 22. Add Auth Shell

Status: open

Replace the single dashboard component with proper app routes.

Done when:

- Login page exists.
- Invite accept page is routed normally.
- JWT is stored and attached to API requests.
- Logged-out users are redirected to login.
- Route guards are tested.

### 23. Add Admin User Management UI

Status: open

Build UI for inviting and managing users.

Done when:

- Admins can invite users.
- Invite links can be copied.
- User status and role are visible.
- Forms use ZardUI components and Tailwind utilities.
- Error and loading states are implemented.

### 24. Add Server Management UI

Status: open

Build screens for adding and checking servers.

Done when:

- Server form supports public/private key input.
- Private key value is never rendered after submit.
- Server check status is visible.
- Default proxy can be selected.

### 25. Add Project And Environment UI

Status: open

Build project and environment management.

Done when:

- Users can create projects and environments.
- Project duplication entry points are visible.
- Empty/loading/error states are implemented.

### 26. Add Service Deployment UI

Status: open

Build the main service creation and deployment workflow.

Done when:

- Docker image, Compose, and Dockerfile modes exist.
- Credentials and env vars can be attached.
- Deploy/restart actions show workflow status.
- Logs and deployment output are visible.

### 27. Add Domain And Proxy UI

Status: open

Build domain configuration and proxy preview/apply UI.

Done when:

- Users can create domains.
- Nginx/Traefik can be selected where supported.
- Proxy preview is readable and copyable.
- Apply status is visible.

### 28. Add Telemetry Settings UI

Status: open

Make platform-only telemetry opt-in from the UI.

Done when:

- Admins can enable/disable telemetry.
- Endpoint and service name can be configured.
- UI clearly states telemetry covers Sango only.
- Tests cover form validation.

## Observability And Security

### 29. Add Structured Audit Events

Status: open

Record platform actions without storing secrets.

Done when:

- User invites, login failures, deploys, restarts, and config applies emit audit events.
- Audit events are queryable by admins.
- Secrets and app log contents are never recorded.

### 30. Add Telemetry Redaction Tests

Status: open

Make redaction behavior explicit and hard to regress.

Done when:

- Tests cover tokens, SSH keys, env values, Docker passwords, and app logs.
- Exported spans/logs never include secret values.

### 31. Add Security Headers And Allowed Hosts

Status: open

Harden HTTP serving defaults.

Done when:

- Backend includes appropriate security headers.
- Allowed host checks are configurable.
- CORS is configurable and not permissive in production.

## Documentation

### 32. Add API Examples

Status: open

Document common API workflows.

Done when:

- Docs show login, invite, create project, add server, create service, deploy,
  restart, logs, and proxy preview.
- Examples use safe placeholders.

### 33. Add Deployment Guide

Status: open

Document production self-hosting.

Done when:

- Guide covers config file, secrets, JWT keys, Postgres, Temporal, frontend,
  backend, worker, and proxy.
- Guide covers backup and upgrade basics.

### 34. Add Architecture Guide

Status: open

Explain boundaries for contributors and AI agents.

Done when:

- Docs cover routes, services, entities, Toasty, Temporal, telemetry, frontend,
  CLI, and MCP.
- Docs explain where business logic belongs.

### 35. Add Documentation Website

Status: open

Create a public documentation website for users, operators, API consumers, and
contributors.

Depends on:

- Item 32, API Examples.
- Item 33, Deployment Guide.
- Item 34, Architecture Guide.

Done when:

- A docs website app or static site lives in the monorepo.
- The site has sections for getting started, installation, configuration, API
  usage, deployment concepts, CLI/MCP, telemetry, security, contributing, and
  architecture.
- Docs content is sourced from version-controlled markdown or MDX.
- Local development and production build commands are documented.
- The site can be built in CI.
- Navigation and search are available.
- The visual design follows [DESIGN.md](./DESIGN.md).
